검증한 결과. **결론: 4종 전부 수용 — clone-only 합성 전략 확정.**

- 실험일: 2026-07-10 / 원본: A사 분기검토보고서(IFRS, editver 5.107)
- 사용자 편집기: editver **5.113** / 절차: 열기 → 표시 확인 → 미리보기 → 재저장
- 도구: `spike/make_variants.py`(변형 생성) · `spike/analyze_resave.py`(재저장 diff 분석)

## 편집기가 재저장 시 고쳐 쓰는 것 (실측 — 우리 편집과 무관)

1. **SPAN 정규화**: 원본에 있던 SPAN 래핑 노드를 평문으로 병합
   (`<TD><SPAN>…</SPAN></TD>` → `<TD>…</TD>`, P 안의 SPAN 런 병합).
   4종 모두 정확히 같은 2곳(원본 유래) — 표시 텍스트는 완전 동일.
   → 우리 파서의 `complex` 노드 개념과 정확히 일치. **v1의 "complex 셀 편집 시
   평문 강등" 설계가 편집기 자체 동작과 같음이 입증됨.**
2. **meta.xml editver 스탬프**: 5.107 → 5.113 (편집기 버전 기록 — 도구는 불변 유지가 옳음).
3. ZIP 엔트리 구성·순서 불변. PGBRK 불변. WIDTH/HEIGHT **재계산 없음**.

## Track A 구현 확정 규칙

- **R1(합성 표 거부) 해소**: 같은 문서 표의 원시 바이트 복제 + inner 텍스트 치환은
  편집기가 그대로 수용한다. WIDTH 재계산이 없으므로 **템플릿 WIDTH 값 복제로 충분**
  — compose.py에 산술 재계산 로직 불필요(동일 열수 한정).
- **표 삭제** = 표 범위 + 선행 구분자 1개 제거로 확정.
- **주석 재번호** = 헤딩 P `replace_inner`로 확정.
- **롤포워드의 TU 편집 허용 확인**(최대 리스크 해소): AUNITVALUE 속성과 표시 텍스트를
  함께 바꾸면 수용. v1의 "TU 수정 금지" 가드는 **사용자 실수 방지용으로 유지**하되,
  롤포워드 엔진은 내부 경로로 TU를 프로그램 편집한다.
- 골든 테스트 주의: "편집기 재저장본"과 비교할 때는 SPAN 정규화·editver 차이를
  허용해야 한다 (도구 자체 무수정 왕복 계약과는 무관).

## V5 — A1 합성 표 (2026-07-11 추가 검증)

A1 compose가 만드는 **재조립 합성**(템플릿의 여는부분+헤더행 복제+경계+본문행
복제+닫는부분 — 스파이크 V1의 통짜 복제와 다른 새 바이트 배열)을 검증:
흥구 주석 17에 문단 1 + 표(헤더 1행·본문 3행) 신설 후 편집기 확인.

- 사용자 확인: 열기·표시(주변 표와 동일 모양)·미리보기 전부 정상.
- 재저장 diff: 재작성 hunk **기존과 동일한 2곳(원본 유래 SPAN 정규화)뿐** —
  합성 표·문단은 바이트 그대로 존속. → **A1/A2 합성 방식 최종 확정.**
